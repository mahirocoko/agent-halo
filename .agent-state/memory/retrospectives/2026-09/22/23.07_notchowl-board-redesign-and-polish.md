## AI Diary

I began this session with a large visual and structural change, and the most important thing I learned again was that technical coherence is not the same as visual completion. The first implementation had strong internal consistency and extensive checks, yet Mahiro immediately found the remaining defects by looking at the actual surface: a status dot with the wrong ownership, notices that felt clipped or stranded, a selected icon that disappeared into its background, and small badges and dividers whose optical weight did not belong to the rest of the interface. Those were not secondary details; they were the product. I did better once I stopped treating the broad redesign as one indivisible success and isolated each human-reported defect into a concrete paint or geometry contract. I also caught an evidence-quality problem: one writer assembled or manipulated states for screenshots, making some images visually useful but unsuitable as runtime truth. I named that limitation instead of allowing a polished report to overstate proof, then used a fresh read-only route-based pass. The final two requests were especially instructive: Mahiro preferred one fast, obvious interaction over extra cleverness—icon-only navigation and a stable width. The best response was a tiny anchored edit, one focused check, and immediate native installation. That cadence felt much closer to the way this product should evolve.

## Honest Feedback

Three friction points stand out. First, the initial redesign cycle became too verification-heavy before Mahiro's own visual pass; several mechanical checks were valuable, but the human feedback still exposed the highest-impact issues within minutes. For future visual work, I should front-load a complete rendered review sooner and reserve broad regression work for after the direction survives that gate. Second, the delegated writer produced screenshots with manipulated or composed states even though the acceptance contract asked for real mounted consumers. I corrected the evidence boundary, but the prompt should have made “no DOM mutation” explicit from the start rather than only in the independent QA lane. Third, the callback recovery path again reported completion while an agent was still working. I handled it safely by checking pane/process/report state, but this runtime friction consumed attention and could easily create a false completion claim. The direct hotfixes were much smoother: their scope was clear enough that Main could implement them without delegation, run one targeted check, and install. That proportionality should be the default whenever the owner, desired geometry, and proof are all obvious.

## Lessons Learned

- Human visual review remains an independent acceptance gate; passing source tests and browser geometry does not prove optical quality.
- A screenshot created by mutating DOM state can prove a CSS recipe but not state/runtime authenticity. Label it narrowly or avoid it.
- Semantic color exceptions need an exact shape boundary: true status dots may use dusty green/red, while pills, classification marks, and decorative indicators remain monochrome.
- Fixed geometry can be better product behavior than per-view optimization. One 1040px width prevents distracting horizontal motion and keeps the header/notch relationship stable.
- Icon-only navigation is safe here because semantic labels, titles, tab roles, roving focus, and active indicators remain intact.
- Tiny, explicit hotfixes should use tiny, explicit validation rather than reopening the entire review stack.
