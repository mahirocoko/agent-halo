## AI Diary

The useful turn in this session was listening to the visual symptom instead of
defending the earlier CSS contract. The first release fix proved that a tray
could own overflow and that its declarations were present, but it did not prove
that the rendered scrollbar was the one Mahiro was seeing. When he described it
as visible but oversized and strange, the source showed a stronger hypothesis:
the narrow dashboard and tray could both scroll, while only one of them had
custom scrollbar paint. That explained why the browser test could pass while a
native-looking scrollbar still appeared in the actual surface. The first
minimal owner correction was the right diagnosis, but Mahiro then explicitly
chose a ScrollArea route. I kept that route local and bounded rather than
installing a library, because this app has no existing ScrollArea dependency
and the requested target is one known Usage surface. The implementation now
owns its thumb geometry and keeps the actual content viewport as the source of
truth. I am deliberately not calling this visual acceptance: the technical
browser proof and Tauri install are strong, but Mahiro still needs to judge the
thumb's optical weight and feel in the real app.

## Honest Feedback

Three friction points were material. First, the earlier regression asserted
native `scrollbar-width: thin` and `scrollbar-color`, so it failed as soon as
the intentionally selected ScrollArea hid the native scrollbar; the test was
correctly stale, but the contract migration was not planned up front. Second,
the initial custom component tracked the total scroll height but not a fully
explicit `aria-valuenow`/maximum model, which made the first implementation
technically usable but less robust for assistive state; that was tightened
before closeout. Third, the automated browser checks can prove ownership,
wheel, keyboard, drag, and computed paint, but they cannot decide whether a
6px custom thumb feels visually right in the native macOS/Tauri surface. The
remaining human gate is therefore real, not a missing test to paper over.

## Lessons Learned

- A passing scrollbar CSS assertion does not prove the user is seeing that
  scrollbar; inspect the complete scroll-owner hierarchy.
- A custom ScrollArea should keep the viewport as the source of truth and make
  keyboard, pointer drag, resize, content mutation, and ARIA state explicit.
- Native/browser regression expectations must be updated when the contract
  intentionally moves from platform scrollbar paint to a custom thumb.
- Technical ScrollArea PASS is not visual/product acceptance.
