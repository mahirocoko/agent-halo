## AI diary

I started with a useful constraint: the new choices should change when our existing assertion is requested, not introduce another sleep mechanism. Keeping the native command boolean and leaving its ownership unchanged made the mode matrix straightforward. The migration also mattered more than the label: mapping an old enabled toggle to continuous On would have silently changed the user's power behavior. Agent was the correct preservation of intent.

I did not get the control anatomy right on the first pass. A select could express the modes, but Mahiro wanted all three options visible. Once he made that preference explicit, I changed only the control and its owned styling rather than reopening the feature. Native radios then gave us a simpler, demonstrable arrow-key path.

The most important verification moment was refusing a clean story from the first reviewer. Its geometry did not match the screenshot, and its keyboard test changed selectedIndex itself. Those were not equivalent to the claims in its PASS table. I kept the valid persistence and layout findings, corrected the warning, and explicitly rejected the keyboard proof. The later segmented session actually used trusted key input. I still separate that browser result from installed native UI acceptance and physical sleep behavior. The elapsed session was too long for this modest feature; I want the next bounded correction to reach the accepted anatomy and exact proof sooner, without spending time on reassuring but weak reports.

## Honest feedback

1. **Initial anatomy missed the user's preferred interaction.** The approved concept did not require a dropdown, yet I chose one and then needed a second implementation pass. The existing Setup segmented recipe was available. I should have made the concrete control choice visible before committing to that shape, without turning it into a large UX exercise.
2. **Reviewer claims needed more disciplined proof.** The first report mixed wrong-row geometry, an inaccurate narrow viewport name and synthetic keyboard assignments with PASS language. Main's screenshot and source audit prevented those claims from becoming acceptance. The next prompt explicitly prohibited property assignment and required genuine key events, which was more useful than another generic review.
3. **Wall-clock closeout was disproportionate.** The transcript spans about an hour for a small feature, while build logs account for only part of that interval. I cannot attribute every gap to compilation or model waiting. I should collect terminal reports promptly, keep the verification scope small, and report known elapsed versus measured execution separately.

## Lessons and promotion

Preserve the old setting's intent during enum migration; visible exclusive choices fit native radio semantics; synthetic event dispatch plus direct state assignment does not prove trusted input; screenshot labels and PASS tables are claims, not verification. These decisions are already covered by existing guidance or the current domain contract. **Retrospective-only; no durable reference learning promoted.**
