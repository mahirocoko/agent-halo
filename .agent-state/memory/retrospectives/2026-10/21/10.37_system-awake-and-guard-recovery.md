## Session summary

Mahiro asked whether agents can continue while the Mac is locked. We separated screen locking, display idle sleep and system sleep, then agreed to keep the system awake during agent work while allowing the display to sleep. Implementation adds a separate On/Agent/Off control, defaulting to Agent without changing the old display preference or migration. Native persistence and independent assertion release were checked in the installed app. Release authorization followed the technical review; an actual locked-screen endurance test remains unperformed.

## AI diary

I started with a small question that could easily have produced the wrong feature. Keeping a screen lit is not the same outcome as keeping local work running, and locking a screen does not mean that the machine has gone to sleep. I am glad that I separated those concepts before changing code. The resulting product decision is modest: two explicit controls with familiar native radio behavior, rather than a silently expanded meaning for the old setting. That preserved both the user's existing preference and a clear explanation of what the application is actually preventing.

The difficult part was operational rather than algorithmic. My tools failed after child creation, and the implementation notifications arrived without a usable parent inspection path. I had to distinguish a worker's completion from my own ability to verify it. Repeatedly saying that I was blocked was honest, but it also made progress feel fragmented. The later owner-coordinated regression gave the interruption a useful outcome: an independent review exposed two lifecycle gaps, and another fresh review checked the repairs without taking over source ownership. Once the tools remained healthy, the installed application's AX controls and pmset gave stronger evidence than another browser screenshot could have provided. I still cannot turn that evidence into an unperformed locked-screen endurance test, so the release must retain that boundary.

## Honest feedback

1. The guard outage interrupted the main task several times, and I initially had only truncated worker notifications. Reporting a partial result was necessary, but the user had to ask for retries and clarification. A better handoff states the exact remaining verification gate once and keeps the primary feature status distinct from diagnostic work.
2. Native automation was not immediately reliable. AXPress alone did not open the collapsed notch consistently, while focusing the control and sending Space did. Relaunch also encountered a short process-exit race. These are harness limitations, not evidence of a preference-persistence defect; only the later observed controls and assertions support the final claim.
3. The implementation was not ready for publication merely because targeted checks passed. The explicit release request triggered version alignment and full browser regression. This extra work is justified, but it should remain bounded to Halo rather than absorbing the neighboring guard project's unfinished canonical checks or implying that a source release includes a signed desktop installer.

## Lessons and reference-learning gate

- Independent system/display assertions need independent settings, confirmation and lifetime ownership. Their actual macOS power effects should not be described as forcibly independent OS sleep policies.
- Browser mocks prove policy and transitions; installed AX controls plus pmset prove a narrower live native path. Neither proves unattended lock-screen endurance.
- Parent-tool health must be tested while a real child is active and again after its terminal result when diagnosing lifecycle binding.
- Retrospective-only; no durable lesson promoted. Existing repository keep-awake contracts and native-persistence rules already own the reusable decisions. Guard repairs belong to mahiro-pi, not a second Halo policy file.
