## AI diary

I initially treated an upstream repair as a stronger explanation than it deserved. The missing Gemini card and the upstream description looked closely aligned, and the port had good unit coverage. Those facts established that one incomplete Cloud response could be supplemented safely from another host using the same token. They did not establish that either host represented the same quota projection that Mahiro actually uses. Seeing the restored card was therefore progress, but it was not the outcome. The user's comparison supplied the disconfirming evidence that my earlier test boundary lacked.

I am more satisfied with the second investigation because it preserved contradictory results instead of hiding them behind another patch. The existing credential reproduced the wrong values. A separate credential still reproduced them. Sandbox variants did not justify another source preference. The useful boundary was the installed CLI's own documented read-only command, which returned structured quota without an agent turn. I could then remove the experimental auth work rather than shipping speculative complexity. I also had to think about failure semantics: silently falling back after a timeout would reintroduce the very numbers we had proved misleading. Returning unavailable is less visually comforting, but it is more honest. The local two-day retrospective streak is a modest continuity signal, not evidence that this reasoning was automatically good. The important improvement was changing the claimed proof from passing fixtures to a sanitized real-reader comparison, then separately testing the rendered status and bounded subprocess behavior.

## Honest feedback

1. The first closeout was too optimistic about the relationship between upstream similarity and the user's actual data. I did state the installed-UI acceptance limit, but I should have requested or obtained a direct value comparison before presenting the restored meters as a likely fix. The screenshot correction was not a cosmetic follow-up; it invalidated the sufficiency of the causal story.
2. Diagnosis took too long and crossed several hypotheses. Checkpoints eventually made the rejected credential and host explanations explicit, but the investigation would have been more economical if the CLI's documented structured usage command had been checked earlier. Read-only capability claims must still be verified; using a generic print prompt without that evidence would have been unacceptable.
3. The verification infrastructure had its own limits. The UI specialist lacked execution tools, so Main performed rendered checks instead of pretending to have independent visual QA. A resize transition detached the fixture node and required a fresh reload. The release gate also exposed an unrelated keyboard-test failure and a tiny bundle overrun. I kept those findings visible, reran bounded checks, and avoided modifying unrelated feature behavior or increasing budgets merely to obtain a green result.

## Lessons and reference-learning gate

- An upstream fix plus passing tests is not proof that two quota surfaces represent the same source, account, projection or reset window.
- Compare sanitized real values before changing credential preference. Keep each source's complete snapshot separate; do not fill unknown account boundaries with plausible numbers.
- A known inaccurate fallback should not silently replace an installed authoritative source after a timeout or malformed response.
- Weekly quota can constrain a nominally full short window. Preserve the raw bucket value while describing actual availability truthfully.
- Retrospective-only; no durable lesson promoted. Existing repo native-verification, privacy and last-good contracts, and Fable's runtime-evidence rules already own the transferable decisions. No competing policy file is needed.
